# Heartbeat-watchdog supervision for the long-poll Telegram bot

The long-poll Telegram bot (`botcmd.sh`) is a single-process, single-threaded shell loop that handles every panel tap and command sequentially. A one-off `kill -0` liveness guard (`botcmd-start.sh` cron) restarts the process if it *dies*, but cannot detect when it is *wedged* — alive but stuck on an open pipe with no writer. In August 2026 the loop wedged and remained unresponsive for 18+ hours; the panel was dead and no self-healing occurred. We added a **heartbeat watchdog**: the loop stamps `/tmp/botcmd.hb` each iteration; the cron watcher now also checks the heartbeat age and kills+respawns the process if it is stale for more than 120 seconds. This was chosen over procd/process supervision because the project's established operational pattern is cron-based, and the heartbeat approach is stateless, self-documenting, and catches *any* wedge mechanism without requiring root-cause diagnosis of BusyBox ash internals. The balance callback was also moved to read from a local cache file (refreshed every 15 minutes) so that the panel never blocks on the live ISP API; this eliminates the most likely trigger for a future wedge while the watchdog remains in place for any other cause.

**Considered options:** PID-liveness only (failed), procd/service supervision (heavier, not the project pattern), inotify/file-watcher watchdog (more moving parts, no benefit over cron).

**Consequences:** Every deployment of the bot now requires the heartbeat file to be written; a pre-heartbeat running process will not be killed by the watcher (safe rollout). The cron watcher gains two file reads (`botcmd.pid`, `botcmd.hb`) per minute, which is negligible.
